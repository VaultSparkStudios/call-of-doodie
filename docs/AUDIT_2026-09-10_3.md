# Audit — 2026-09-10 (Session 175)

**Method.** S171-S173 each pre-verified the TASK_BOARD backlog and each correctly
found it saturated. S174 went one layer out and measured the *gates* instead.
This session went one layer out again and measured the **claims** — every
number the game states to a player, checked against the code that actually
produces it.

That choice was made because the previous four sessions all closed with the
same honest gap: *no new player-facing value*. Auditing player-facing truth is
the one audit lens that can close a real player-facing defect without inventing
gameplay scope on a launch-sensitive branch.

**Premise verification.** Every finding below was confirmed against live code
before being written down. Two candidate findings were **discarded during the
audit** for failing that bar; they are recorded in §Non-findings so a future
session does not re-open them.

## Finding 1 — BOT ROYALE has published two different bot counts for ten sessions

**Severity: SIL:3 · player-facing · confirmed**

`src/modes/botRoyale.js` has spawned `BOT_COUNT = 16` bots since S165, which
raised the royale to a sixteen-bot, two-screen scrolling arena. The runtime
changed. The copy did not. Four *live* player-facing surfaces still claimed
twelve:

| Surface | Reaches the player via | Claim |
|---|---|---|
| `src/config/modeCatalog.js` blurb | in-game mode picker | `12 bots · shrinking flood` |
| `src/config/modeCatalog.js` description | `/modes/` page | `against twelve bots` |
| `src/content/fieldManual.js` §5 | `/field-manual/` + in-app reference | `twelve bots and a shrinking flood` |
| `public/gameplay-contract.json` | published machine-readable claim | `against twelve bots` |

Meanwhile `src/config/changelog.js:32` correctly advertises "sixteen bots on a
scrolling two-screen arena". **The repo published both numbers at once.**

Two things made this invisible:

1. `modeCatalog.js` calls itself "single source of truth for game-mode
   identity", and it is — for *identity*. Labels, ids, colors, and the
   `REPLAY_MODES` ordering are all pinned by `modeCatalog.test.js`. The
   **numbers inside its prose had no authority behind them at all.**
2. The generated surfaces were correctly generated. `validate-public-contract`
   and `check-public-claims` both passed, because `public/gameplay-contract.json`
   faithfully reproduced its source. The source was simply wrong — the same
   green-but-wrong shape S174 found in the gate layer.

The S167 TASK_BOARD line "Public roadmap/changelog now describe the sixteen-bot
scrolling royale" was true of the changelog and false of everything else.

**Root fix, not a copy edit.** A literal corrected by hand would drift again on
the next balance change. `src/config/modeFacts.js` becomes the authority; the
mode runtime imports its constants *down* from it, and player-facing prose is
composed *up* from it. This is the rule already governing `silScore` and
`silAvg3` in `write-project-status.mjs`: a value that is a function of
something else is derived, never typed.

Bundle constraint respected: `modeFacts.js` is dependency-free, because
`modeCatalog.js` is read by `App.jsx` at zero cost under the S163 bundle diet.

## Finding 2 — the mode-fact drift class had no gate

**Severity: SIL:2 · confirmed**

`check-public-claims.mjs` already pins achievement, theme, META-node, zombie-
variant, weapon and enemy counts. It did not cover mode prose, and — more
importantly — it read only *source* modules. No test and no gate read the
**generated** public artifacts, which is exactly where a wrong source becomes a
published claim.

Extended to walk `PLAYER_FACING_MODE_FACTS` across both source copy and the
generated `public/gameplay-contract.json` / `public/field-manual.json`. On first
run it immediately failed on the stale generated contract — the intended
behavior, proven rather than asserted.

**Deliberately out of scope:** dated changelog entries. The September 3 entry
says "twelve bots" because twelve bots is what shipped that day, and the
September 9 entry records the raise. Rewriting a dated record to satisfy a
current constant would falsify history — the opposite of the gate's purpose.
The exclusion is documented in the gate itself.

## Finding 3 — the genome ledger is not a clean ledger (S174 SIL commitment)

**Severity: SIL:2 · confirmed, partially corrected**

S174 committed `[SIL:1] genome-history honesty pass for duplicate/out-of-order
session labels`. Measured against the data:

- **Duplicate labels: real.** S123 and S162 each appear twice. Cause found: the
  control-plane writer upserts on the composite key `(date, session)`, so
  re-snapshotting a session on a later date appends instead of updating. S162
  has rows dated 2026-08-26 and 2026-09-03.
- **Coverage gaps: real, and worse than the brainstorm knew.** S164, S165, S171
  and S172 have no snapshot at all — four closeouts that skipped the §3.7
  genome renderer. This is the same class S174 closed for `STATE_VECTOR`, and
  S174's own currency gate cannot see it, because it reads only the maximum
  label.
- **"Out-of-order": NOT supported by the data.** All 50 labels are monotonically
  non-decreasing. There is no reversed label. Recorded as a correction.
- **"A snapshot labelled 166 carrying S167 prose": not mechanically provable.**
  S166's `overallStatus` does equal S167's, but `overallStatus` legitimately
  persists unchanged across consecutive sessions — the same string is shared by
  24 of 50 rows, most of them certainly correct. Gating on it would fire on half
  the file. Dropped rather than shipped as a finding.

**Not rewritten.** The ledger is append-only evidence; deleting duplicates or
back-filling four missing snapshots would fabricate closeouts that never ran.
The known defects are declared as an explicit dated baseline in code — visible,
counted in every report, and never silently forgiven — and the gate fails on
anything new. This follows S165's precedent of recording a reused session number
"rather than papering over it".

**Writer fix is cross-repo.** `append-genome-snapshot.mjs` proxies to
`vaultspark-studio-ops`. Per CANON-018 no sibling tree is edited from here; the
`(date, session)` upsert-key defect is reported as Ark cargo.

  class is closed rather than the instance.

  block only, so it had nothing to drift. Checked, not assumed.
