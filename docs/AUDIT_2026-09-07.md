## A1 · [P0 · correctness] BOT ROYALE bots target themselves, so the flagship new mode is inert

**Premise (verified).** `src/modes/botRoyale.js:93` publishes *every* alive bot into the shared
target-candidate list:

```js
gs._targetables = bots.map((b) => ({ x: b.x, y: b.y, alive: true, kind: "bot", id: b.id }));
```

`src/systems/enemyFrame.js:33-39` (`pickTarget`) walks that list for **each** enemy and keeps the
nearest candidate, with **no self-exclusion**:

```js
const extra = gs._targetables || [];
for (let i = 0; i < extra.length; i += 1) {
  const s = extra[i];
  if (!s || s.alive === false) continue;
  const d = Math.hypot(s.x - e.x, s.y - e.y);
  if (d < bestD) { best = s; bestD = d; }
}
```

For a bot `e`, the candidate carrying `e`'s own id sits at distance **0**, which beats the player and
every rival unconditionally. So each of the twelve bots steers toward the point it is already
standing on and aims its ranged fire at itself. The mode's own header comment promises "twelve bots
… fight you and each other"; today the only bot-versus-bot damage is the incidental bullet sweep in
`botRoyale.step`, and the bots never advance on the player at all.

The existing royale test asserts `gs._targetables.length` and flood/win behaviour, so it passes while
the actual free-for-all does not happen. This is a phantom-green surface, not a covered one.

**Ship.** Give `pickTarget` an identity-aware skip (a candidate whose `id` matches the enemy's own id
is never a target), keep the zone/structure path byte-identical, and add a regression court that
proves a royale bot picks a *rival* and that a zone-mode enemy still picks its zone.

## A2 · [P0 · feature] A real scrolling world camera, an arena larger than the screen, and sixteen bots

**Premise (verified).** There is no camera. The world *is* the viewport: `gameLoop` reads
`const W = GW(), H = GH()` (`src/App.jsx:2460`) and hands those to movement clamps, spawn placement,
the flow field (`enemyFrame.js:62-69`), and the flood ring. `botRoyale.init` seeds bots on a circle of
`Math.min(W, H) * 0.42` and defines the flood at `Math.hypot(W, H) / 2` — all viewport units.
`BOT_COUNT = 12`. A battle royale that fits entirely on one screen has no map to rotate through, no
approach to read, and no reason to move.

`src/drawGame.js:193-210` already opens exactly the seam this needs: one `ctx.save()`, the
trauma-shake translate, then the ADS `translate/scale/translate` — with screen-space HUD painted after
the matching `restore()`. A camera translate slots in there without disturbing either.

**Ship.** A pure, unit-testable `src/systems/camera.js` (deadzone follow, arena clamp, `worldToScreen`
/ `screenToWorld`), an arena size carried on the run state that **defaults to the viewport** so every
existing mode is byte-identical, per-mode opt-in via the mode definition, the camera transform applied
at the drawGame seam, pointer/touch aim converted through `screenToWorld`, the prerendered background
tiled across the arena, movement and spawn clamps moved to arena bounds, and `BOT_COUNT` 12 → 16 on a
2× arena.

## A3 · [P1 · readability] Camera-correct threat readability: radar, flood ring, off-screen arrows

**Premise — corrected during implementation.** Two of the three premises I first wrote here were
wrong, and following the code rather than the report is what caught them. Recorded rather than
quietly deleted:

* *Wrong:* "the flood ring is painted in screen space and would detach from the world." It is drawn
  inside `drawModeLayer`, which `drawGame.js:458` calls **inside** the world block, well before the
  restore. It was already camera-correct and needed no change.
* *Wrong:* "there is no minimap anywhere in `src/`." `grep -i minimap` does return nothing, but the
  feature exists under a different name — the "Mini-radar" at `drawGame.js:1373`, a player-relative
  blip ring over a 0.6-viewport window. Searching for the noun instead of the behaviour produced a
  phantom gap.
* *Correct, and the one that mattered:* the off-screen threat compass is genuinely camera-blind. Its
  own module header states "The arena is a fixed W×H field (no scrolling camera)", and
  `getOffscreenThreatArrows` tests enemy **arena** coordinates against a `0..W`/`0..H` **screen**
  rect. With a scrolled camera the focus itself leaves that rect and every arrow is wrong.

Floating combat text was a fourth, unlisted case found the same way: it carries arena coordinates but
is drawn after the world transform is restored, which is invisible while arena == viewport.

Pillar 1 of `context/SOUL.md` is **"Readable chaos … threats, controls, cooldowns, objectives, and
competitive-integrity state must remain legible."** A2 is only shippable if this ships with it.

**Ship.** Give `getOffscreenThreatArrows` a `camX`/`camY` arena→screen offset so the compass keeps
working under a scrolled camera; shift floating combat text by the camera; and promote the existing
Mini-radar to a whole-arena plot (arena extent, flood ring and its next close, player, rivals) when —
and only when — the arena is larger than the viewport.

## A4 · [P1 · performance] DeathScreen diet — 101.8 KB arrives at the worst possible beat

**Premise (verified).** From the baseline build: `DeathScreen-C7lSONR7.js` is **101.84 kB**
(32.58 kB gzip) — the largest non-vendor lazy chunk in the app, larger than `HomeV2`'s logic and 1.6×
`combatRuntime`. `src/components/DeathScreen.jsx` is 103,445 bytes and owns three separate canvas
contexts (lines 115, 240, 253) for score-card rendering. It is fetched at the exact moment the run
ends — the beat Pillar 2 ("humiliation becomes revenge") depends on landing fast.

**Ship.** Split the score-card/share-canvas machinery and the deep archive panels out of the
first-paint path so the death beat renders on a small chunk and the heavy share surface streams in
behind it. Hold the runtime gate and the public contract.
